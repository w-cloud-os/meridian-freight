# Meridian Freight: Delivery Delay Analytics

A reproducible PostgreSQL + Docker pipeline that answers one question: **what is causing late deliveries?** Built as a practice contract for a fictional logistics company. All data is **synthetic**, generated by a seeded script.

## Summary
Delays are driven mainly by route distance: every additional 100 km adds about 5.9 minutes of delay. One crew, crew 2, runs about 15 minutes later than the others on every shipment. Once distance and crew are accounted for, weekend shipments run only about 3 minutes later than weekday ones, which is small next to an average delay of about 44 minutes.

The raw weekday-vs-weekend comparison is misleading: weekdays look slightly worse (44.7 vs 43.7 minutes) only because crew 2 works weekdays. Fitting all factors together separates the effects.

## Tech stack
PostgreSQL 16, Docker Compose, Python (NumPy, SciPy, psycopg), SQL

## Project structure
```

```

## How to run
**1. Start the database**
```bash
cp .env.example .env              # then edit the password
docker compose up -d              # starts PostgreSQL and creates the schema
```
The database is exposed on host port **5433**, because 5432 may be taken by a local install.

**2. Set up Python**
```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

**3. Load the synthetic data** (safe to re-run; it clears the tables first)
```bash
python scripts/generate_data.py
```

**4. Run the analysis**
```bash
for f in sql/*.sql; do docker compose exec -T db psql -U meridian -d freight < "$f"; done
python scripts/analysis.py
python scripts/regression.py
python scripts/multiple_regression.py
```
The output should match the numbers in the Findings section below.

To reset the database completely: `docker compose down -v`, then `docker compose up -d` again.
Note: the database is exposed on host port **5433**, because 5432 may be taken by a local install.

## Design decisions
- **Delay is computed, not stored.** It's derived from `delivered_at - promised_at` through the `shipment_delays` view, so it can never drift out of sync with the source columns.
- **Indexes on `shipments(route_id)` and `shipments(crew_id)`.** Postgres indexes primary keys automatically but not foreign keys, and my joins and group-bys use these columns. The cost is extra disk space and slightly slower writes.
- **Constraints** such as `CHECK (distance_km > 0)` and `delivered_at >= shipped_at` reject bad data at the database level instead of relying on every script to behave. For example, making delivered_at < shipped_at means a parcel was delivered before it ever got shipped.
- **`timestamptz`** for event times, so values mean the same moment regardless of session time zone.
- **numeric** for distance and weight instead of floating point, so stored values are exact.

## Generator assumptions (synthetic data)
Delay in minutes for each shipment is generated as:

`delay = -5 + 0.06 * distance_km + 3 * weekend + 15 * (crew 2) + Normal(0, 25)`

- 12 routes with distances between 50 and 1,200 km; 6 crews (3 weekday, 3 weekend).
- Weekend shipments are only handled by weekend crews, and crew 2 is a weekday crew. This deliberately makes the weekend flag and the crew effect tangled together (confounding).
- ~2% of shipments are left undelivered (still in transit) to exercise NULL handling.
- Seeded (`seed=42`), so every run produces identical data.

## Findings
### Weekend vs weekday (raw comparison)
           shipments    mean delay (min)    standard deviation (min)
weekday    14,019       44.7                32.8
weekend    5,570        43.7                31.8

The raw gap is about -1 minute: weekends look slightly better.

Welch t-test results (scripts/analysis.py):

All crews     : weekend minus weekday = -1.03 min, 95% CI (-2.02, -0.03), t = -2.02, df = 10550, p = 0.043
   scipy check: t = -2.02, p = 0.043
Excluding crew 2: weekend minus weekday = 3.84 min, 95% CI (2.78, 4.89), t = 7.12, df = 11787, p = 1.2e-12
   scipy check: t = 7.12, p = 1.2e-12
   
### Delay by route distance (simple regression)
Fitting delay = slope * distance + intercept gives:

method                                     slope (min/km)     intercept (min)
closed form (least squares)                0.05944            0.12
gradient descent, standardized distance    0.05944            0.12

That is 5.94 minutes of extra delay per 100 km, close to the true 0.06. R² = 0.365 and the residual standard deviation is 25.9 minutes: distance explains about a third of the variation in delay.

Gradient descent and feature scaling. Distances run up to 1,200 km, so the loss is extremely steep in the slope direction (curvature around 2 * mean(x^2), over a million) and nearly flat in the intercept direction (curvature around 2).

setup                                         result
raw distance, lr = 0.05                       diverged (nan)
raw distance, lr = 1e-7, 5,000 steps          slope 0.05958, but intercept stuck at 0.0001 and MSE 672.7 (optimum is about 671)
standardized distance, lr = 0.1, 500 steps    matches the closed form exactly

Standardizing (z = (x - mean) / std) puts both parameters on a similar scale so one learning rate works for both. To convert back to the original units: slope = w_z / std and intercept = b_z - w_z * mean / std.

### All factors together (multiple regression)
Solving the normal equations (X^T X) beta = X^T y with distance, a weekend flag, and a crew 2 flag:

term                  true value     estimate      std error      95% CI
intercept (min)       -5             -4.42         0.48           (-5.36, -3.47)
distance (min/km)     0.06           0.0595        0.0005         (0.0585, 0.0606)
weekend (min)         +3             +3.33         0.43           (2.49, 4.16)
crew 2 (min)          +15            +15.05        0.45           (14.16, 15.94)

Residual standard deviation is 25.2 minutes (the generator's noise is 25) and R² = 0.399. Every true value falls inside its 95% interval, so the model recovers what the generator put in. Note that the weekend effect is +3.3 here but -1 in the raw comparison: adjusting for crew removes the confounding.

### Delay by crew
Crew 2 runs about 15 minutes later per shipment than the other crews, after accounting for distance and weekend.
Statistical strength: the estimate is roughly 33 standard errors from zero, so it’s very unlikely to be chance.
In distance terms: 15 minutes equals the delay from about 250 extra km of route (15 ÷ 0.0595).
Against the noise: the typical shipment-to-shipment variation is about 25 minutes, so crew 2’s effect is real and meaningful but doesn’t make every one of its parcels late. It shifts the whole distribution.
Company-wide impact: crew 2 handles roughly a quarter of delivered shipments (a third of the weekday volume, and weekdays are about 72% of the total). So removing its extra delay would cut the average delay by roughly 3.5 minutes out of about 44.

## Limitations
- Data is synthetic, so real-world results would be messier.
-  T-test Assumptions:

1. Independent observations. Each shipment’s delay should not influence another’s.
2. The sample mean is roughly normal. With thousands of shipments per group, the central limit theorem makes this safe even when individual delays are skewed. Welch’s version also drops the equal-variance assumption.
3. No serious outliers or heavy tails dominating the means.
4. The comparison is meaningful. The test only measures whether two averages differ, and says nothing about why.

- Where it can fail in this project:

• Confounding is the big one. Nothing was randomized, so the weekend and weekday groups differ in other ways.
• Independence is probably violated in real data. Shipments on the same route, with the same crew, or on the same bad-weather day move together. The generator draws each delay independently, so it can’t show this, but with real data standard errors would be too small and p-values too optimistic.
• Missing deliveries.
• Huge samples make trivial effects significant. With about 20,000 rows, even a 1-minute gap gets a tiny p-value. 
• Means can hide the story. A t-test says nothing about the tail, such as the share of parcels more than two hours late, which is what customers notice.

- What the analysis can't tell about causation:
• “Crew 2” is a label, not a cause. The +15 minutes belongs to everything about crew 2: its drivers, vehicles, supervisor, depot, or the kinds of parcels it gets. The data can’t say which one is responsible.
• With only 12 routes, distance can’t be separated from “which route.” Each route has one distance, so the slope could partly reflect route-specific things that happen to correlate with distance (border crossings, traffic, extra handoffs). More distinct distances, or repeated measurements per route, would help.
•Weekend and weekend crews are perfectly tangled. Weekend crews only work weekends, so the data can’t tell “weekends are slower” from “weekend crews are slower.” That’s the same collinearity behind the dummy-variable trap.
• Unmeasured confounders could hide or fake effects. Here the model matches the generator exactly (linear, additive, nothing missing), which is why it recovers the truth so cleanly. Real data is rarely that kind. In real work you’d say “adjusted for X, Y, Z,” not “caused by.”
• The roughly 2% in-transit shipments were dropped. If the unfinished ones are disproportionately the late ones (likely in real life), delays are underestimated.
• Standard errors assume independent, equal-variance noise. Shipments on the same route or crew are probably correlated, which would make the true uncertainty larger than the intervals suggest.
• Statistically significant isn’t the same as important. The weekend effect is real but small next to the 25-minute noise.
